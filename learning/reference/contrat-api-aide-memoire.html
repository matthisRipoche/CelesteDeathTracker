Relire un contrat d'API

À garder sous la main quand Claude propose une route.

Les quatre questions

  1. Qui appelle ? Navigateur (session + CSRF) ou mod (token Bearer).
  2. Que contiennent la requête et la réponse ? Nom, type, unité, obligatoire ou facultatif, pour chaque champ.
  3. Que se passe-t-il quand ça va mal ? Le code d'erreur et la réaction du client.
  4. Comment ça évolue ? Qui lit déjà ce champ ?

Où est le contrat dans ce projet ?

Pas dans un seul fichier. Il est écrit dans le texte (docs/data-model.md, CLAUDE.md), dans le code Java de l'API (c'est lui qui fait foi), dans face.model.ts (site) et dans Payloads (mod). Rien ne vérifie que les quatre concordent : après tout changement de champ, demande à Claude la liste de tous les endroits qui le lisent.

Casse-t-il quelqu'un ?

ChangementRisque
Ajouter un champ facultatif dans une réponseSans danger si le client ignore ce qu'il ne lit pas.
Ajouter une routeSans danger.
Renommer ou retirer un champCasse tout client qui le lit.
Rendre un champ de requête obligatoireCasse les clients qui ne l'envoient pas (l'ancien mod).
Changer un type ou une unitéCasse en silence : les chiffres deviennent faux.

Les codes du projet

CodeSens dans ce projet
200Lecture réussie.
201Une mort a été créée (/api/ingest/deaths).
202Événement de tentative reçu, traité ensuite (/api/ingest/events).
400Requête invalide : champ absent, side hors A/B/C.
401Pas connecté, ou mauvais type d'accès (token sur une route de site, cookie sur l'ingestion).
404Rien pour ce compte : une face ou une room jamais jouée.

À refuser d'office

  • Un identifiant d'utilisateur dans le corps d'une requête du mod : le compte vient du token.
  • Un champ qui change de nom sans que le site et le mod soient mis à jour avec lui.
  • Une route de lecture qui ne filtre pas par compte.
