Aide-mémoire : les 4 questions

Leçon 1 · Contrats d'API · 10 minutes

Lire un contrat d'API

Quand Claude te propose une route, tu peux l'accepter ou la refuser en toute connaissance de cause, avec quatre questions.

Ce que tu sauras faire à la fin : relire un contrat proposé, dire s'il casse un client existant, et repérer ce qui n'a rien à faire dedans.

Un contrat, c'est une promesse écrite

Un contrat d'API dit, entre deux programmes, ce que l'un demande et ce que l'autre répond : la route, ce qu'on envoie, ce qu'on reçoit, et ce qui se passe quand ça va mal. Dans le monde OpenAPI, c'est un fichier « lisible par une machine » qui décrit l'API, utile parce qu'une documentation écrite à la main est souvent floue, incomplète ou périmée (OpenAPI, introduction).

Dans ce projet, il n'y a pas de fichier OpenAPI : le contrat n'existe pas en un seul fichier. Il est recopié à plusieurs endroits (voir plus bas), et c'est une des choses à garder en tête quand tu relis une proposition.

Exemple 1 : la route que nous venons de construire

La page « détail d'une room » appelle ceci. Lis-le comme un contrat :

GET /api/faces/room?sid=Celeste/1-ForsakenCity&side=B&room=01

200 {
  "room": "01",  "side": "B",  "position": 2,  "roomCount": 3,
  "previousRoom": "00",  "nextRoom": "02",
  "entries": 4,  "stops": 2,  "stopRate": 0.5,
  "deathsTotal": 1,  "lastDeathAt": 21000,
  "points":   [ { "deathId": 7, "x": 1, "y": 2, "first": true, ... } ],
  "outcomes": [ { "attemptId": 1, "outcome": "cleared", ... } ]
}                                       (extrait : champs tronqués)

Source : FaceController.java, FaceDtos.java et FaceFlowTests.java.

RéponseQuand
200La room existe pour ce compte.
400side n'est pas A, B ou C : « le serveur ne peut ou ne veut pas traiter la requête à cause d'une erreur côté client » (MDN).
401Pas de session ouverte, ou un token de mod au lieu d'une session.
404Aucune tentative de ce compte n'a atteint cette room. Un autre compte reçoit aussi 404 : pour lui, elle n'existe pas.

Exemple 2 : le mod envoie une mort

Ici l'appelant n'est plus le navigateur mais le mod C#, qui tourne chez le joueur : un code client que le serveur ne peut pas croire sur parole.

POST /api/ingest/deaths
Authorization: Bearer cdt_...        (jamais de cookie de session)

{ "timestamp": 1760000000000,  "chapter": "Celeste/1-ForsakenCity",
  "room": "01",  "deathX": 6853,  "deathY": -2200,
  "totalDeaths": 35012,  "sessionDeaths": 1,  "timeInRoomMs": 41000,
  "attemptId": "…",  "side": "B",  "saveSlot": 0 }

201 Created

Source : docs/data-model.md (type DeathEvent) et FaceFlowTests.java.

  • Obligatoire ou facultatif ? Tous les champs de DeathEvent sont obligatoires, sauf attemptId, side et saveSlot. Si deathX manque, l'API répond 400 : Jackson 3 refuse un champ numérique absent (CLAUDE.md).
  • Pourquoi ces trois-là sont facultatifs ? Parce que l'ancien mod, encore installé chez des joueurs, ne les envoie pas. Le contrat doit rester vrai pour les anciens clients.
  • Qui est le joueur ? Le serveur le déduit du token. Il n'y a jamais d'identifiant d'utilisateur dans le corps : un client peut mentir sur son corps, pas sur le token que le serveur a émis.
  • 201 ou 202 ? Une mort est enregistrée tout de suite : « une nouvelle ressource a été créée » (201). Un événement de tentative (POST /api/ingest/events) répond 202 : « reçu, pas encore traité » (MDN).

Exemple 3 : faire évoluer sans casser

Pendant le cadrage de la page room, j'avais prévu une liste recent dans la réponse, puis je l'ai retirée du contrat avant d'écrire le code : le site la calcule déjà à partir de points. Retirer un champ avant que quelqu'un le lise ne coûte rien. Après, c'est autre chose.

Changement du contratLe site Angular
Ajouter un champ facultatif bestStreakContinue de marcher : il ignore ce qu'il ne lit pas.
Renommer stopRate en rateCasse : face.model.ts et la page lisent stopRate et afficheraient « NaN % ».
Rendre obligatoire un champ que le mod n'envoyait pasCasse l'ancien mod (400 sur chaque mort).

Deux sources disent la même chose avec leurs mots. Fowler décrit le Tolerant Reader : un client qui n'extrait que ce dont il a besoin survit à l'ajout de champs (Martin Fowler). Le guide d'API de Microsoft range parmi les changements cassants le fait d'ajouter un champ obligatoire plus tard, de retirer un champ obligatoire ou de rendre un champ facultatif obligatoire (Azure REST API Guidelines). Le cas « renommer » n'y est pas listé : c'est une conséquence, parce qu'un renommage équivaut à retirer un champ et à en ajouter un.

Où vit le contrat dans ce projet ?

Pour la même route, les mêmes champs sont écrits plusieurs fois :

OùCe que c'est
docs/data-model.md, « Contrat API » de CLAUDE.mdLe texte, pour décider et relire.
FaceDtos.java, DeathRequest.javaCe que l'API fait réellement.
face.model.tsCe que le site croit recevoir.
Payloads, dans le mod C#Ce que le mod croit devoir envoyer.

Qui fait foi ? Le code Java de l'API, parce que c'est la seule version qui s'exécute. Le texte peut devenir faux sans que rien ne le signale. Et aucun de ces fichiers ne vérifie les autres : seuls les tests d'API contrôlent ce que le serveur répond. Si un champ est renommé côté API seulement, le site et le mod ne s'en aperçoivent qu'à l'exécution (le « NaN % » de l'exemple 3).

Il existe une manière d'avoir un vrai fichier unique : OpenAPI. On peut soit le générer depuis le code (il décrit alors toujours ce que l'API fait vraiment), soit l'écrire d'abord et en tirer le code (plus rigoureux, plus lourd). Ce n'est pas fait ici ; la première option serait la plus simple si le projet grossit. En attendant, une question à poser à Claude pour chaque contrat : « quel endroit fait foi, et que se passe-t-il s'il dévie des autres ? »

Les quatre questions à poser

  1. Qui appelle ? Le navigateur (session + CSRF) ou le mod (token Bearer) ? La mauvaise réponse ouvre une faille.
  2. Que contiennent la requête et la réponse ? Chaque champ : son nom, son type, son unité, obligatoire ou facultatif.
  3. Que se passe-t-il quand ça va mal ? Le code (400, 401, 404…) et ce que fait le client.
  4. Comment ça évolue ? Qui lit déjà ce champ ? Ajouter est presque toujours sûr ; renommer, retirer ou rendre obligatoire casse quelqu'un.

À toi : cinq relectures

Réponds sans regarder plus haut. Le retour est immédiat.

1. Le mod envoie une mort sans le champ deathX. Que répond l'API ?

2. Lequel de ces changements casse la page Angular de la room ?

3. Claude propose d'ajouter userId dans le corps de POST /api/ingest/deaths. Que réponds-tu ?

4. Pourquoi attemptId, side et saveSlot sont-ils facultatifs dans DeathEvent ?

5. Claude renomme un champ dans FaceDtos.java et met le texte à jour. Qu'est-ce qui peut encore être faux ?
