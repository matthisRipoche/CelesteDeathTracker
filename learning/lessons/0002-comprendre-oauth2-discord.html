Comprendre OAuth2 avec Discord

Quand Claude te propose une connexion « via un fournisseur », tu dois savoir qui parle à qui, ce qui doit rester secret, et ce qui protège de la triche.

Ce que tu sauras faire à la fin : suivre les 6 étapes de la connexion Discord du projet, dire quelle donnée passe par le navigateur et laquelle n'y passe jamais, et relire une proposition d'auth avec cette grille.

Le problème : prouver qui tu es sans donner ton mot de passe

Ton site veut savoir qui est le joueur. Discord le sait déjà. Mais le joueur ne doit pas donner son mot de passe Discord à ton site. OAuth2 est la méthode où Discord donne à ton site une autorisation limitée, après que le joueur a dit « oui » chez Discord.

Les trois rôles

La norme (RFC 6749, §1.1) les définit ainsi :

RôleDéfinition de la normeDans le projet
Resource owner« une entité capable d'accorder l'accès à une ressource protégée »Le joueur
Client« une application qui fait des requêtes au nom du resource owner »Ton API Spring Boot
Authorization server« le serveur qui émet les jetons d'accès au client »Discord

Attention au vocabulaire : ici, le « client » est ton serveur, pas le navigateur ni le mod. Le navigateur ne fait que transporter des redirections.

Les 6 étapes (flux « authorization code »)

Ce flux est celui de DiscordOAuthConfig.java : AuthorizationGrantType.AUTHORIZATION_CODE.

#Qui → quiCe qui se passe
1Joueur → ton APIClic sur « Continuer avec Discord » : GET /api/auth/oauth2/discord.
2Ton API → navigateur → DiscordRedirection vers https://discord.com/oauth2/authorize avec client_id, scope=identify, redirect_uri et state.
3Joueur ↔ DiscordLe joueur se connecte chez Discord et clique « Autoriser ». Ton site ne voit rien de cela.
4Discord → navigateur → ton APIRedirection vers /api/auth/oauth2/callback/discord?code=…&state=…. Le code est un ticket à usage court, pas une identité.
5Ton API → Discord (direct)POST https://discord.com/api/oauth2/token avec le code et le secret client. Discord répond avec un access token.
6Ton API → Discord (direct)GET https://discord.com/api/users/@me avec Authorization: Bearer <access token>. Réponse : id, username, global_name, avatar.

Sources : doc OAuth2 de Discord (adresses, code, échange contre un token, state) et DiscordOAuthConfig.java (adresses et scope réellement configurés).

Puis ton code prend le relais : DiscordOAuth2UserService.loadUser reçoit ces infos, trouve ou crée le compte du site, et la session s'ouvre (cookie JSESSIONID, comme pour un mot de passe). À partir de là, OAuth2 n'intervient plus.

Pourquoi deux allers-retours ? Ce qui ne passe jamais par le navigateur

Le navigateur voit les étapes 2 et 4 : l'URL et le code sont visibles (historique, extensions, journaux). C'est pourquoi le code ne suffit pas : il faut le secret client pour l'échanger (étape 5), et cet échange se fait de serveur à serveur. Les clients web doivent garder ce secret confidentiel : « Web application clients MUST ensure confidentiality of client passwords » (RFC 6749, §10.1).

Dans le projet : le secret vient de DISCORD_CLIENT_SECRET (secret GitHub, puis .env du serveur), jamais du code Angular ni du dépôt. Le client_id, lui, n'est pas un secret (§2.2).

Le paramètre state : empêcher qu'on te fasse connecter au compte d'un autre

Sans protection, un attaquant pourrait te faire cliquer sur un lien de retour qui contient son code : tu te retrouverais connecté à son compte, ou lié à son Discord. La parade : le client envoie une valeur imprévisible à l'étape 2, la garde de son côté, et refuse le retour si elle n'est pas identique à l'étape 4. La norme dit que la valeur « MUST contain a non-guessable value » (§10.12) ; Discord le recommande aussi : « denier la requête » si elle ne correspond pas.

Dans le projet, nous n'avons écrit aucun code pour cela : c'est Spring Security (oauth2Login dans SecurityConfig.java) qui le gère. Je l'ai vu dans le comportement attendu de Spring, mais la page de doc lue pour cette leçon ne le détaille pas : c'est un bon point à me demander de vérifier dans le code de Spring.

L'adresse de retour : pourquoi elle doit être identique des deux côtés

L'adresse de l'étape 4 est déclarée chez Discord et construite par Spring ({baseUrl}/api/auth/oauth2/callback/{registrationId}). Si elles diffèrent d'un caractère, Discord refuse. C'est aussi une protection : le code n'est renvoyé qu'à une adresse que tu as choisie à l'avance. C'est ce que tu as fait dans le portail développeur, et pourquoi la prod, Docker et ng serve ont chacun leur ligne.

Dans le projet : le même flux sert à deux choses

  • Se connecter : pas de compte connecté, donc resolve trouve ou crée le compte à partir de l'id Discord.
  • Rattacher : POST /api/auth/discord/link (session + CSRF) note en session quel compte demande, puis le flux part vers Discord. Au retour, loadUser lit cette note et rattache.

Cette note est la raison pour laquelle l'API a besoin d'un POST avant la redirection : c'est le seul moyen de faire passer « qui demande » à travers le détour par Discord.

Ta grille de relecture : 4 questions

  1. Qui est le client OAuth2 ? Ton serveur. Si une proposition met le secret dans le navigateur ou le mod, refuse.
  2. Que demande-t-on à Discord ? Le scope. Ici identify : pseudo et avatar, ni email, ni serveurs. Plus de scope, plus de risque et plus de confiance demandée au joueur.
  3. Qu'est-ce qui protège le retour ? state et adresse de retour exacte.
  4. Que devient l'identité ensuite ? Un compte du site et une session ordinaire. Le token Discord n'est pas conservé ici.

À toi : quatre relectures

1. Claude propose de faire l'échange du code contre un token depuis Angular. Que réponds-tu ?
